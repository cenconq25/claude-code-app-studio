# Retro / Milestone Event Hooks Reference

Some of the most valuable hooks fire **infrequently** — at sprint
boundaries, at the moment a release tag is pushed, at the close of a
beta cycle. They don't enforce code quality. They surface
cross-cutting reflection that the team would otherwise put off.

This doc describes the **pattern**, not a wired hook. Adopt it once
your team has a steady sprint cadence; until then, run the
underlying skills (`/retrospective`, `/milestone-review`) by hand.

## What we're building

A hook that detects a "retro-worthy" event in git history and triggers
the right skill automatically:

| Event | Detection | What runs |
|---|---|---|
| Sprint end | A `sprint-*-end` git tag is pushed | `/retrospective` |
| Milestone close | A `milestone-*` tag is pushed | `/milestone-review` |
| Release candidate | A `rc-*` or `release-*` tag is pushed | `/launch-checklist` (read-only mode) |
| Hot patch closed | A `hotfix-*` tag is pushed | `/postmortem` (lightweight) |
| Beta close | A `beta-*-end` tag is pushed | `/playtest-report` aggregation |

The trigger is git-tag-based because tags survive across sessions,
machines, and team members in a way that ad-hoc dates do not.

## Three ways to wire it

### Option 1 — GitHub Actions (recommended)

The CI runner has the right permissions, the right credentials, and a
machine identity. It also doesn't require every team member to have
the hook installed locally.

```yaml
# .github/workflows/sprint-end.yml
name: Sprint Retrospective

on:
  push:
    tags:
      - 'sprint-*-end'

jobs:
  retro:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Identify sprint
        id: sprint
        run: |
          tag="${{ github.ref_name }}"
          slug="${tag%-end}"
          echo "slug=$slug" >> $GITHUB_OUTPUT

      - name: Run /retrospective via Claude Code
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          npx --yes @anthropic-ai/claude-code \
            --print \
            "/retrospective ${{ steps.sprint.outputs.slug }} \
             --output production/sprints/${{ steps.sprint.outputs.slug }}-retro.md"

      - name: Open PR with retro doc
        uses: peter-evans/create-pull-request@v6
        with:
          branch: retro/${{ steps.sprint.outputs.slug }}
          title: "Retrospective: ${{ steps.sprint.outputs.slug }}"
          commit-message: "docs: add retrospective for ${{ steps.sprint.outputs.slug }}"
          body: |
            Auto-generated by sprint-end hook.
            Review and edit before merging.
```

Why this is the recommended option:
- Reproducible across all contributors with no local install.
- Clean audit trail (the workflow run is the audit).
- Output lands as a PR, so the team reviews and edits the retro
  before it's "official".
- Keeps secret credentials (the API key) off developer machines.

### Option 2 — Local git hook

Useful for solo developers and very small teams.

```bash
#!/usr/bin/env bash
# tools/git-hooks/post-push
# Symlink as .git/hooks/post-push (requires git 2.45+) or call from
# a wrapper around `git push`.

set -uo pipefail

# Read pushed refs from stdin: "<local-ref> <local-sha> <remote-ref> <remote-sha>"
while IFS=' ' read -r local_ref local_sha remote_ref remote_sha; do
  case "$local_ref" in
    refs/tags/sprint-*-end)
      slug=$(basename "$local_ref")
      slug=${slug%-end}
      echo "Sprint end detected: $slug — running /retrospective"
      claude --print "/retrospective $slug \
        --output production/sprints/${slug}-retro.md"
      ;;
    refs/tags/milestone-*)
      slug=$(basename "$local_ref")
      claude --print "/milestone-review $slug \
        --output production/milestones/${slug}-review.md"
      ;;
    refs/tags/release-*)
      slug=$(basename "$local_ref")
      claude --print "/launch-checklist $slug --read-only \
        --output production/releases/${slug}-readiness.md"
      ;;
  esac
done

exit 0
```

Versions of git before 2.45 don't ship `post-push`. The portable
fallback is a wrapper:

```bash
# tools/scripts/release-tag.sh
git tag "$1"
git push origin "$1"
.claude/hooks/retro-event-dispatch.sh "$1"
```

### Option 3 — Harness-side via Notification

Wire a `Notification` hook that listens for a structured "tag pushed"
message and dispatches. This is the lightest-weight option but
requires that `git push` happen *inside* a Claude Code session.

```bash
#!/usr/bin/env bash
# .claude/hooks/notify.sh excerpt
INPUT=$(cat)
MSG=$(printf '%s' "$INPUT" | jq -r '.message // empty')

if printf '%s' "$MSG" | grep -qE 'sprint-[a-z0-9-]+-end pushed'; then
  slug=$(printf '%s' "$MSG" | grep -oE 'sprint-[a-z0-9-]+-end' | head -1)
  slug=${slug%-end}
  echo "::next-action::/retrospective $slug" >&2
fi
```

The `::next-action::` line surfaces a suggested skill invocation in
the model's view; it doesn't run automatically.

## Why tag-based triggering

A few alternatives all fall short:

- **Date-based** (cron at sprint end). Misses irregular sprints,
  fires on cancelled sprints, fires when no one's around.
- **Branch-based** (merge to `release/*`). Captures release readiness
  but not sprint cadence.
- **Manual command** (`/retrospective` typed by hand). Easy to skip;
  retros that get skipped are exactly the ones the team most needs.
- **Push-count-based** (every N commits). Arbitrary; mobile sprints
  are scope-bounded, not commit-bounded.

Tags are intentional, named, and survive every workflow path.

## What `/retrospective` produces

The output document, generated automatically when this hook fires,
typically contains:

- **Velocity** — stories closed vs. planned, with reasons for the gap.
- **Cycle time** — time from `In Progress` to `Done`.
- **Bug discovery rate** — bugs filed against this sprint's stories
  vs. backlog bugs closed.
- **Director-gate friction** — which gates failed and re-ran.
- **Theme of pain** — the top 3 root causes surfaced from sprint
  notes, retros, and bug postmortems.
- **Three commitments for next sprint** — concrete actions, owners,
  and exit criteria.

It is intentionally short. A retro that nobody reads is no retro.

## Anti-patterns

1. **Hooking on every commit to `main`** — drowns the team in noise.
   Use tags to mark intentional milestones.
2. **Auto-merging the retro PR** — the team's review *is* part of the
   retrospective. Auto-generation accelerates writing, not deciding.
3. **Wiring the harness Notification hook to publish to Slack
   directly** — confidential context (bug names, customer names)
   leaks. Generate locally, redact, then publish.
4. **Tagging with mutable names** (`sprint-current-end`). Every retro
   needs a permanent identifier so you can compare them later.

## Testing the hook

- Tag a fake sprint end on a throwaway branch:
  `git tag sprint-2026-test-end && git push origin sprint-2026-test-end`
- Confirm the workflow runs (Actions tab) or the local hook fires.
- Confirm the retro doc is generated under the expected path.
- Delete the tag locally and remotely
  (`git push origin :refs/tags/sprint-2026-test-end`).
- Repeat after every change to the trigger pattern — getting a
  retro hook wrong on a real sprint end is annoying.
